# Two skills, not six: fold the disciplines into `issue-finder`, let `issue-fixer` sync and commit locally

v0.1.0 shipped six skills: two user-invoked entry points (`issue-finder`, `issue-fixer`) and four model-invoked disciplines (`exploratory-testing`, `verifying-findings`, `screening-duplicates`, `drafting-issues`) that `issue-finder` called in sequence on every run. In practice no run ever used a discipline standalone in a materially different way than `issue-finder` already drove it, so the six-way split bought cross-skill handoff overhead (each call re-states context across a skill boundary) without buying real optionality. It also split skills.sh install telemetry six ways for one conceptual tool, which hurts discoverability for no behavioral benefit.

v0.1.0 also required an `ENGAGEMENT.md` ledger, written once up front, naming yes or no for every external action including ordinary git operations (commit, push, rebase, force-push). That model assumed a long-lived, possibly multi-session engagement. The new flow is one `issue-finder` run immediately followed by zero or one `issue-fixer` run in the same conversation, so a separate ledger file read by name later adds a file and a round of upfront questions for a shape of engagement that no longer needs them.

## Decision

**Two skills.** `issue-finder` absorbs what the four disciplines did as internal steps with their own reference files (`references/project-types.md`, `references/scoring.md`). `issue-fixer` keeps the fix-only boundary from v0.1.0: it only ever touches one already-confirmed finding per run.

**Local git operations are pre-authorized, not ledger-gated.** `issue-finder`'s sync step stashes dirty work (never dropped), fetches, and fast-forwards or replays the primary branch onto its freshly fetched upstream tip (aborting and restoring on conflict), then branches into `bughunt/<date>-<sha>`. `issue-fixer` commits locally on its own `fix/<slug>` branch. None of this needs an upfront ask, because none of it is destructive: hunt and fix commits land only on those new branches, a stash is never dropped, and a conflicting rebase aborts and returns the checkout to the branch the user started on. The primary branch itself is updated to that fetched tip (fast-forward, or its own unpushed commits replayed on top). Every other local branch stays where it was. This supersedes [ADR 0003](0003-authorization-ledger-not-frontmatter-flags.md)'s blanket "every external action defaults to no, including ordinary git operations" for exactly these bounded, reversible operations.

**Push, opening a public issue, opening a PR, and submitting a security report still default to no**, asked for explicitly in chat at the point each would fire. No ledger file backs this; the ask and the action happen in the same run, so there is nothing that needs to outlive the conversation the way `ENGAGEMENT.md` was designed to.

**`issue-fixer` becomes model-invoked.** It drops `disable-model-invocation: true` and the matching `openai.yaml` policy block. This amends [ADR 0001](0001-user-invoked-entry-points.md) for the fixer specifically: once `issue-finder`'s scorecard step asks which finding to fix and the user names one, `issue-finder` hands off to `issue-fixer` by a Skill-tool call in the same turn, instead of making the user separately type `/issue-fixer <id>` as a second manual step. This is safe to allow because `issue-fixer` cannot act without a specific, already-confirmed `IF-###` ID the user just named, unlike a bare "fix something" trigger a harness might infer from an offhand remark. Direct `/issue-fixer <id>` invocation, bypassing `issue-finder` entirely, still works and still requires the finding's record to already say `Confirmed`. `issue-finder` itself keeps `disable-model-invocation: true`: a full run is still expensive and long-running enough that it must never fire from a casual remark.

## Still true, unchanged

A security-sensitive finding is never pushed, never opened publicly, and never named in a commit message, regardless of what the user authorizes for ordinary findings. `issue-fixer` refuses a dirty tree and refuses to start from anything but a freshly fetched upstream tip. Neither skill hard-resets or force-pushes. Replaying the primary branch's own unpushed commits onto its fetched upstream tip is the sync step above. Rebasing those commits onto any other ref, or rewriting any other branch, still needs a separate, explicit ask.
