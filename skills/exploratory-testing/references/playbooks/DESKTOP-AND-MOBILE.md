# Playbook: desktop (GTK/GNOME, Electron) and mobile apps

Native UI needs a different driving mechanism than a browser; the same verb set (navigate/launch, snapshot, click/type, capture logs, screenshot, record) still applies, bound to whatever tool this harness provides.

- **GTK/GNOME apps**: run from a terminal to capture stderr/warnings live (GTK prints critical warnings there that never surface in the UI). Use the platform's accessibility tree (AT-SPI) for a structural snapshot where a driving tool exposes it, rather than relying on screenshots alone. Check behavior across the two most recent stable GNOME releases if both are available, since that's the project's own documented support window (see `drafting-issues/references/AI-DISCLOSURE-POLICIES.md` for how this affects what's reportable). Check D-Bus and portal interactions (file chooser, notifications) specifically, since these are common integration-boundary bug sites.
- **Electron apps**: drive via CDP (Chrome DevTools Protocol) the same way a web UI is driven (`WEB-UI.md`'s verb set applies to the renderer process), plus check the main-process/renderer IPC boundary directly: a message with an unexpected shape sent across that boundary is a cross-component-contract lead.
- **Mobile (iOS/Android)**: where a device/simulator and a driving tool are available in the sandbox, test permission-dialog flows explicitly (deny then retry, revoke mid-session), backgrounding and resuming mid-operation, and rotation/orientation changes mid-flow; these are the state-loss bug sites specific to mobile lifecycle.
- For any of the above, test what happens when the app is closed and reopened: does state persist as documented, or is something silently lost?
- Honest limit: if this harness has no way to drive a native GUI at all (no accessibility tooling, no CDP, no device), say so explicitly as a capability boundary in `capabilities.md` and fall back to the Guidebook tour (install + run from a terminal, exercise via keyboard where possible) rather than skipping the target entirely.
